#! Part VII · The four studies

# Part 1 (RQ1) · Context management

## The question and the design

**Research question.** How should retrieved graph evidence be selected, ordered and trimmed so that the answer survives a fixed context budget?

Graph evidence is the part of the evidence that can grow fastest: a two-hop neighbourhood of an institution can contain hundreds of authors and papers and thousands of relations. Context management decides what of it reaches the model. RQ1 compares five ways of doing that while everything else is held fixed.

Table: RQ1 design {w=1.6,4.6}
| Element | Setting |
|---|---|
| Cohort | 32 generated validation questions = 8 families × 4 variants (normal, noisy, conflict, unanswerable); source combinations G, TG, GS and TGS, 2 families each |
| What changes | Only how the graph evidence is selected, ordered and pruned |
| Graph input | One immutable, hashed graph candidate pool per question, identical for all five methods (below) |
| Text and structured evidence | Generated once by the unchanged baseline serialiser and passed through unchanged for every method |
| Budget | 24,000 characters in total, shared equally over the sources the question uses (all 24,000 for graph-only questions; 12,000 per source for two sources; 8,000 for three) |
| Answer | One call of the shared answer model per question; CM-03 additionally makes one keyword-extraction call |
| Runs | 5 methods × 32 questions = 160 records; 192 model calls (160 answers + 32 keyword calls); 0 errors |

#### The shared graph candidate pool

To compare context managers fairly, they must all start from the same graph evidence. For every question the pool is materialised once from the seed entities that the B2 retriever recorded: a breadth-first traversal to depth 2 with at most 256 base nodes, 1,024 base traversal edges and 128 edges per expanded node. For noisy variants the distractor graph paths are added uniformly, under hard caps of 320 nodes and 1,536 edges. The pool is hashed and handed unchanged to each method; no method can retrieve anything outside it. Explicit conflict overlays on the graph stay tagged, are never turned into official relations, and reserve the same share of the budget for every method. The pool treats the graph as undirected for optimisation but keeps each relation's real direction in the written evidence.

## The five strategies

### CM-B0 · raw order (control)

**Idea.** Do nothing clever: write the graph evidence in the order the pool lists it until the budget is full.

**Algorithm.** Take node and edge records in candidate order; serialise each record whole (records are atomic, never cut in the middle); append records while they fit in the graph share of the budget; stop at the first record that does not fit.

**Cost.** No model call and no scoring; the context step takes about {{RQ1.CM-B0.cm_ms}}.

@figure figures/m_cm_b0.png | CM-B0 (raw order): records are appended in retrieved order until the next one no longer fits. | 6.2

### CM-B1 · fixed top-K (control)

**Idea.** Keep only the five best-ranked papers and the graph paths that explain why each was found.

**Algorithm.** Rank the candidate papers in retriever order (path length, then seed rank, then node ID); keep the first five papers within graph depth 2; add the parent paths that connect each kept paper to its seed entity; serialise in deterministic depth-first order.

**Cost.** No model call; about {{RQ1.CM-B1.cm_ms}}. It keeps on average {{RQ1.CM-B1.selected_graph_nodes}} nodes and {{RQ1.CM-B1.selected_graph_edges}} relations, a context of {{RQ1.CM-B1.context_tokens}} tokens.

### CM-01 · KG²RAG-inspired

**Origin.** KG²RAG (knowledge-graph-guided retrieval-augmented generation) expands retrieved chunks through a knowledge graph and organises the result into connected subgraphs before generation. The original links text chunks to the graph triples extracted from them. STaRK has no such extraction provenance, and inventing it would leak text into the graph view, so the project approved a **graph-native adaptation** before any result existed.

**The adaptation: provenance units.** One unit per official relation, written deterministically from labels and IDs only:

- WRITES: "Author ‹a› writes Paper ‹p›."
- AFFILIATED_WITH: "Author ‹a› is affiliated with Institution ‹i›."
- CITES: "Paper ‹A› cites Paper ‹B›."
- HAS_TOPIC: "Paper ‹p› has topic ‹f›."

Units carry IDs, types, graph labels (a paper's title) and the relation; they never contain abstracts, years, dates, venues, citation counts or ranks. A derived inverse row maps to the same official edge and therefore to the same unit (stable ID `graph:official:‹8-digit edge ID›`). Unnamed entities stay unnamed; an ID is never turned into an invented name.

**Algorithm.**

1. Build the provenance units of every relation in the candidate pool.
2. Embed the question and every unit with MiniLM and score each unit by cosine similarity to the question.
3. Take the **10** most similar units as seeds (inside the candidate pool only, so CM-01 cannot become a global retriever).
4. Expand **one hop** around the seeds, again inside the pool.
5. Split the expanded graph into connected components.
6. Build a **maximum spanning tree** per component with Kruskal's algorithm, edge weight = cosine(question, unit), ties broken by unit ID.
7. Write each tree in **depth-first order**, rooted at its highest-weight edge.
8. Score the trees with the pinned cross-encoder reranker `BAAI/bge-reranker-large` (revision `55611d7…`, CPU float32, two threads, batch size 1, 512-token pairs).
9. Remove duplicate units and pack trees into the graph budget in rank order.

**Fallbacks.** If units exist but no usable structure, the method keeps semantic units only (`graph_semantic_units`); with no units at all the graph context is empty (`no_graph_relation_evidence`). It never falls back to text. No fallback occurred in the study.

**Cost.** One reranker pass, no extra model call. The context step takes {{RQ1.CM-01.cm_ms}} on average, and the resulting context is the largest ({{RQ1.CM-01.context_tokens}} tokens, {{RQ1.CM-01.selected_graph_nodes}} nodes and {{RQ1.CM-01.selected_graph_edges}} relations kept). A recorded timing asymmetry favours CM-02 and CM-03 in latency: CM-01 computes its question-specific unit scores inside its timer, while the query-specific scores of CM-02 and CM-03 were staged offline.

### CM-02 · G-Retriever-inspired (prize-collecting Steiner tree)

**Origin.** G-Retriever retrieves a compact subgraph by solving a prize-collecting Steiner tree problem: nodes and edges relevant to the question carry prizes, every edge has a cost, and the solver finds one connected subgraph with the best prize minus cost. The original then encodes the subgraph with a graph neural network and soft prompts; the adaptation keeps only the subgraph selection and writes the subgraph as text.

**Algorithm.**

1. Embed node labels and graph-only edge descriptions (the same relation templates as CM-01) with MiniLM and score them against the question.
2. **Node prizes:** the 3 most similar nodes receive prizes 3, 2 and 1; all other nodes 0 (ties by ID).
3. **Edge prizes:** the 5 most similar edges receive prizes 5, 4, 3, 2 and 1; all others 0. Every edge costs **Ce = 0.5**.
4. Solve with the official `pcst_fast` solver (version 1.0.10): unrooted, one tree, Goemans–Williamson pruning; edge prizes are handled by a virtual-node reduction.
5. Serialise the resulting connected subgraph breadth-first and remove the lowest-contribution leaves until it fits the budget.

A disconnected solver output is treated as an error, not silently replaced.

**Cost.** No model call; the solver is fast ({{RQ1.CM-02.cm_ms}}). It keeps the smallest context ({{RQ1.CM-02.selected_graph_nodes}} nodes, {{RQ1.CM-02.context_tokens}} tokens).

@figure figures/m_cm_02.png | CM-02 (G-Retriever-inspired): prizes for the most relevant nodes and edges, a fixed edge cost, and one connected subgraph from the PCST solver. | 6.2

### CM-03 · QAFD-RAG-inspired (query-aware flow diffusion)

**Origin.** QAFD-RAG places mass on seed nodes and lets it diffuse through the graph along query-aware edge weights; nodes that collect enough flow form the retrieved region, with retrieval guarantees in the original analysis (not claimed here). The adaptation follows the specification and the pinned reference implementation for the formulas, and the frozen specification for every parameter.

**Algorithm.**

1. **Keyword extraction:** one model call with a strict JSON prompt returns the question's keywords (cached per question; same model settings and the 1,024-token cap).
2. **Seeds:** each node's seed score is its highest cosine similarity to any keyword; the **20** best nodes become seeds with **mass 10** each.
3. **Edge conductance:** H(u,v) · (1 + 0.25 · (H(u,q) + H(v,q))), where H is the non-negative cosine (cos + 1) / 2 between embeddings and q is the question (coefficients a = 1, b = 1/4 of the reference formula). Nodes without an embedding get no semantic conductance.
4. **Diffusion:** every node can hold at most **1** unit of mass (sink capacity); repeatedly push the excess of the node with the largest excess (ties by node ID) to its neighbours in proportion to conductance.
5. **Stop** when the total excess is at most **ε = 0.05**, or after **1,000,000** pushes, in which case the current support is used.
6. **Support:** nodes with x > **0.01**, plus the connector nodes needed to keep the region connected.
7. Prune the outer nodes with the lowest x until the graph budget fits.

**Cost.** One extra model call (keyword extraction) and a slow diffusion: the context step takes {{RQ1.CM-03.cm_ms}} on average, the largest of all methods. The diffusion converged on only {{RQ1.CM-03.convergence|pct}} of the questions (5 of 32); the rest stopped at the push limit and used their current support.

What the numbers say:

- **Answer quality is near its floor for every method.** All five methods abstained correctly on the 8 unanswerable variants, which alone gives an average F1 of 0.250. CM-B0 and CM-03 returned an empty answer on every one of the 32 questions (precision, recall and F1 all exactly 0.250; answerable F1 {{RQ1.CM-03.answerable_f1}}). CM-01 returned papers on 8 answerable questions, CM-B1 on 6 and CM-02 on 3 (answerability correctness {{RQ1.CM-01.answerability_correctness}}, {{RQ1.CM-B1.answerability_correctness}} and {{RQ1.CM-02.answerability_correctness}}).
- **CM-01 has the best answers** (F1 {{RQ1.CM-01.answer_f1}}, answerable F1 {{RQ1.CM-01.answerable_f1}}, MRR {{RQ1.CM-01.mrr}}) at {{RQ1.ratio.input_tokens.CM-01/CM-B1}}× the input tokens and about 2.3× the latency of CM-B1.
- **CM-B1 is the efficient choice.** It uses about a third of CM-B0's input tokens ({{RQ1.CM-B1.input_tokens}} vs {{RQ1.CM-B0.input_tokens}}) with equal or better F1 and MRR, and it beats CM-B0 and CM-03 on every Pareto axis.
- **CM-02 is the fastest** ({{RQ1.CM-02.latency}}) with the smallest context, but it ranks correct papers lowest (MRR {{RQ1.CM-02.mrr}}) and keeps the fewest of them (gold coverage {{RQ1.CM-02.gold_coverage}}).
- **CM-03 keeps the most correct papers** in the context (gold coverage {{RQ1.CM-03.gold_coverage}}) yet produced no correct answer on any answerable question, and it is by far the slowest ({{RQ1.CM-03.latency}}).
- **Gold coverage is low for everyone:** at most {{RQ1.max.gold_coverage|pct}} of the correct papers reach the context, whatever the method. The candidate pool itself limits what context management can do.

## Is any difference real?

@figure figures/c_rq1_tests.png | RQ1 paired differences in answer F1 with 95 % family-bootstrap intervals and Holm-adjusted p-values. Every interval touches zero. | 6.4

No pair differs significantly: every Holm-adjusted p-value is {{RQ1.test.answer_f1.CM-01~CM-B1.p_holm}}. The observed differences come from very few families: an unadjusted p-value of 0.5 is what the exact test gives when only two families differ, both in the same direction, and 1.0 when at most one family differs. As explained in Chapter 17, with 8 families and 10 pairs no RQ1 difference could have reached significance, so these comparisons are descriptive.

## Findings

1. **No context-management method improved answer quality with statistical support** (all Holm-adjusted p = {{RQ1.test.answer_f1.CM-01~CM-B1.p_holm}}; with 8 families significance was unattainable).
2. **CM-01 had the highest answer F1 and MRR** ({{RQ1.CM-01.answer_f1}}, {{RQ1.CM-01.mrr}}), driven by the two graph-only families, at {{RQ1.ratio.input_tokens.CM-01/CM-B1}}× the input tokens of CM-B1.
3. **CM-B1 is the efficient choice and the overall winner:** a third of the raw control's tokens at equal or better quality, dominating CM-B0 and CM-03.
4. **More correct papers in the context did not mean more correct answers:** CM-03 had the highest gold coverage and no correct answers on answerable questions.
5. **The limit is upstream:** at most {{RQ1.max.gold_coverage|pct}} of the correct papers reached the context for any method, and multi-source questions were never answered.
