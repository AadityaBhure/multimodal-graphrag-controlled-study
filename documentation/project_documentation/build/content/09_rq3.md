# Part 3 (RQ3) · Retrieval control

## The question and the design

**Research question.** Can a policy decide which sources to query, in what order and when to stop, while reducing unnecessary retrieval and without losing answers?

Table: RQ3 design {w=1.6,4.6}
| Element | Setting |
|---|---|
| Cohort | 28 generated validation questions = all 14 families (7 source combinations × 2) × 2 variants (normal, noisy) |
| What changes | Only the retrieval-control policy: which source to query, with what query, in what order, and when to stop |
| Tools | The unchanged retrievers B1 (text), B2 (graph) and B3 (structured), wrapped as tools; results are cached durably with their originally measured latency |
| Evidence memory | Cumulative and de-duplicated across a policy's searches |
| Fixed downstream stack | Context = labelled sections for the sources actually queried, in the order Text → Graph → Structured, **8,000 characters per queried source**; the shared answer model, prompt and parser. No RQ1 pruning and no RQ2 fusion. |
| Runs | 5 policies × 28 questions = 140 records; 0 errors |

The fixed 8,000 characters per queried source is a recorded interpretation of the specification's "fixed per-source budget": it reproduces B4 exactly when all three sources are queried and keeps a source's evidence text identical whichever other sources a policy chose, so the policy is the only variable.

## The shared rule router

A deterministic keyword router decides which sources a question mentions. It is the whole of AR-B1 and the starting point ("base router") of AR-01 and AR-02. Its cue table was frozen before any result and never tuned.

Table: Cue words of the rule router (matched after Unicode NFKC normalisation, lowercasing and whitespace collapsing) {w=1.0,5.2}
| Source | Cues |
|---|---|
| Text | abstract, title, text, content, phrase, wording, mention, mentions, mentioned, contain, contains, containing |
| Graph | author, authors, authored, written by, writes, affiliat…, institution, university, cites, cited by, references, referenced by, topic, field of study (but "citation count" and numeric citation comparisons are structured cues) |
| Structured | year, publication year, date, rank, paper rank, citation count, numeric "N citations", journal, conference, venue, document type, doctype, before, after, between, at least, at most, more than, less than, greater than, fewer than, >=, <=, >, < |

The output is every matched source in the fixed order Text → Graph → Structured; if nothing matches, Text only. Because the generated questions are worded from templates that contain these cue words, the router is somewhat flattered by the benchmark, a limitation stated in Chapter 32. It is not perfect either: the validation templates say "at least one of …" and "at least one author …", and "at least" is a structured cue, so the router adds the structured source to text-only and graph-only questions.

## The five policies

### AR-B0 · always search everything (control)

Query text, graph and structured with the raw question, in that order, for every question; then answer from the fixed context. Three searches and one model call per question.

@figure figures/m_ar_b0.png | AR-B0 (always search everything). | 6.0

### AR-B1 · rule router (control)

Normalise the question, match the cue table, query every routed source once in the fixed order, then answer. No language model, no learning, no gold information.

@figure figures/m_ar_b1.png | AR-B1 (rule router): cue matching decides the sources; each is queried once. | 6.2

### AR-01 · Adaptive-RAG-inspired

**Origin.** Adaptive-RAG trains a small classifier to predict a question's complexity and chooses no retrieval, single-step retrieval or multi-step retrieval accordingly. The adaptation keeps that three-way routing with a `t5-base` classifier and a model-based sufficiency controller for the multi-step route.

**Training data.** Only training material is used. The eligible pool is the 7,993 official training questions plus the 56 generated training questions (8,049). A frozen hash rule splits it: a question goes to the development partition when the first 16 hex digits of SHA-256(question ID), read as an integer, modulo 100 is below 10. The result is **7,302 training and 747 development questions**. (Four of the 14 generated training families straddle the two partitions; this is reported as a limitation.) Validation, test and human-test questions are never read.

**Oracle labels.** A retrieval-only oracle labels each training question with the cheapest route that would have retrieved every correct paper:

- **A (no retrieval)** succeeds only when the correct answer is empty;
- **B (one source)** queries the router's first source once and succeeds if gold coverage is 1.0;
- **C (multi-step)** queries up to three distinct sources with the raw question (router order first, then the remaining sources in the order text, graph, structured) and succeeds if the accumulated gold coverage is 1.0.

The label is the cheapest successful route, or C if none succeeds. The labels are strongly imbalanced, and no rebalancing is allowed by the specification:

@figure figures/c_ar01.png | AR-01: training and development loss per epoch (left; epoch 7 is kept) and the oracle route labels of the training and development partitions (right). | 6.6

**Training.** `google-t5/t5-base` at pinned revision `a9723ea7…`; input = raw question (at most 256 tokens), target = one label token (at most 2 tokens); AdamW with learning rate 3 × 10⁻⁵, weight decay 0.01, batch size 16, seed 42; at most 10 epochs with early stopping after 2 epochs without development-loss improvement; no label smoothing, no oversampling. The best development loss, **0.2170, was reached at epoch 7**, and training stopped after epoch 9.

**Inference.**

1. The classifier predicts A, B or C from the raw question (greedy decoding; an invalid output counts as B).
2. **A:** no retrieval; the answer model sees the question only.
3. **B:** query the router's first source once, then answer.
4. **C:** query the first unqueried routed source; after every retrieval except the third, a **controller call** returns JSON `{sufficient, next_subquery, reason}`. If sufficient, stop; otherwise route the sub-query with the rule router and query its first unqueried source (or the next unqueried source in the order text, graph, structured). At most 3 searches. If the controller's output is still invalid after one schema repair, retrieval stops and the answer uses the evidence gathered so far.

**Behaviour in the study.** The classifier predicted the multi-step route for all 28 questions: 20 runs used all three searches and 8 stopped after the first search when the controller judged the evidence sufficient. It searched exactly the needed graph source on graph-only questions but averaged {{RQ3.AR-01.llm_calls}} model calls and {{RQ3.AR-01.total_tokens}} tokens per question.

@figure figures/m_ar_01.png | AR-01 (Adaptive-RAG-inspired): a trained classifier chooses the route; the multi-step route uses a model-based sufficiency controller. | 6.2

### AR-02 · CRAG-inspired corrective retrieval

**Origin.** Corrective RAG (CRAG) scores retrieved evidence with a lightweight evaluator and triggers corrective actions when the evidence looks ambiguous or wrong. The adaptation uses a pinned cross-encoder evaluator with calibrated thresholds and adds sources instead of web search.

**Evaluator.** `cross-encoder/ms-marco-MiniLM-L-6-v2` (revision `233902d2…`, pairs of at most 512 tokens) scores (question, evidence item) pairs, where an item is rendered as title and abstract (text), title plus the verbalised relation path (graph), or `field: value` lines (structured).

**Calibration (development partition only).** On 745 development questions with a non-empty answer, every evidence item from the unchanged retrievers was labelled 1 if it belongs to a correct paper and 0 otherwise (7,498 items: 1,010 positive, 6,488 negative). A one-dimensional logistic regression (Platt scaling; lbfgs, C = 1, balanced classes, seed 42) maps raw scores to probabilities: **p = 1 / (1 + e^−(0.376 s + 0.102))**.

**State rule and thresholds.** GOOD if the best item has p ≥ UPPER; BAD if every item has p ≤ LOWER (or there is no evidence); otherwise AMBIGUOUS. The thresholds were chosen on 2,235 development retrieval states (641 GOOD, 446 AMBIGUOUS, 1,148 BAD by gold coverage) from the frozen grid LOWER ∈ {0.20, 0.25, 0.30, 0.35, 0.40} × UPPER ∈ {0.60, …, 0.80} by the highest macro-F1, with ties broken by fewer errors, a wider margin, a lower LOWER and a lower UPPER. The selected pair is **LOWER = 0.40, UPPER = 0.75** (macro-F1 0.392).

@figure figures/c_ar02.png | AR-02 calibration: the Platt curve with the GOOD and BAD regions (left) and the macro-F1 of every threshold pair on the development states, with the selected pair outlined (right). | 6.6

**Policy.**

1. Query the router's first source and evaluate the evidence.
2. **GOOD:** stop and answer.
3. **AMBIGUOUS:** add the highest-priority unqueried routed source (or the next unqueried source in the order text, graph, structured).
4. **BAD:** add all remaining sources in the order text, graph, structured.
5. Re-evaluate after each correction; at most **2 correction rounds**. An evaluator failure counts as AMBIGUOUS. If the state is still BAD when no source is left, the answer is generated anyway and the run is marked `insufficient_evidence`.

**Behaviour in the study.** The evaluator rated the evidence GOOD on {{RQ3.stop.AR-02.good}} questions; on {{RQ3.stop.AR-02.sources_exhausted}} it ran out of sources to add and on {{RQ3.stop.AR-02.max_correction_rounds}} it hit the correction limit. The evaluator is a small local model, so AR-02 makes only the one answer call ({{RQ3.AR-02.llm_calls}} per question).

@figure figures/m_ar_02.png | AR-02 (CRAG-inspired): a calibrated evaluator decides whether to stop, add one source or add all remaining sources. | 6.2

### AR-03 · AGENT-G-inspired agent

**Origin.** AGENT-G uses an agent that chooses retrieval actions over a graph, with critic roles that validate answers and comment on failures. The adaptation gives the agent one tool per source and keeps the validator and commentor roles.

**Roles and schemas.**

- **Agent:** "a retrieval controller" that must choose exactly one action from the question, the previous feedback and the current evidence, and return an `AgentAction` JSON: iteration, source (text, graph, structured or stop), retrieval query, domain, entities, relations, structured intent, reason code (textual, relational, numeric, hybrid or correction) and stop reason.
- **Generator:** the shared answer prompt produces a candidate answer from the evidence memory after every search.
- **Validator:** "an evidence-grounding validator" without access to gold answers; returns `{accept, error_type, unsupported_claims}` with error types none, wrong source, wrong entity, wrong relation, insufficient evidence, unsupported answer, structured query error.
- **Commentor:** sees only the question, the last action and the validator's verdict, and returns `{feedback, recommended_source, reason}` to guide the next action. It cannot add evidence.

**Loop.**

1. At iteration i (at most **4**), the agent proposes an action. Malformed JSON gets one repair call; if the repair also fails, the iteration counts and the rule router picks the source.
2. If the action is *stop*, generate the answer from memory and return it.
3. Otherwise run exactly **one tool**, add the new evidence, and generate a candidate answer.
4. The validator accepts or rejects the candidate. Accepted → return it.
5. Rejected at iteration 4 → **INSUFFICIENT_EVIDENCE**, answered as the empty set. Otherwise the commentor gives feedback and the loop continues.
6. **Loop guard:** the same normalised action twice without new evidence forces a fixed feedback ("Previous action produced no new evidence. Choose a different source/action."); a third time ends with INSUFFICIENT_EVIDENCE.

**Behaviour in the study.** The validator accepted a candidate on {{RQ3.stop.AR-03.validator_accepted}} questions and {{RQ3.stop.AR-03.max_iterations_rejected}} ended after four rejected iterations. The agent wasted almost no searches ({{RQ3.AR-03.unnecessary_retrieval}}) but needed {{RQ3.AR-03.llm_calls}} model calls, {{RQ3.AR-03.total_tokens}} tokens and {{RQ3.AR-03.latency}} per question, and the validator accepted unsupported answers on 18 questions (*validator false accept*).

## Why every policy gave the same answers

Answers differ only where the evidence differs, and here the evidence that decides the answer is the same for every policy:

- The **structured-only** questions are answered exactly by every policy (F1 {{RQ3.strata.modality.S.AR-B1.answer_f1}}): every policy reaches the structured retriever, which returns the exact answer.
- The **graph-only** questions score F1 {{RQ3.strata.modality.G.AR-B1.answer_f1}} for every policy: the graph retriever's top-5 holds only a few of the many correct papers.
- **Every other source combination scores 0** for every policy: text conditions are exact phrases that the meaning-based text retriever does not find, and the multi-source answers need all conditions at once.

So the overall answer F1 of {{RQ3.AR-B1.answer_f1}} is (4 × {{RQ3.strata.modality.S.AR-B1.answer_f1}} + 4 × {{RQ3.strata.modality.G.AR-B1.answer_f1}}) ÷ 28 for every policy. Better control of *which* sources are searched cannot help when the searched sources cannot return the answer.

## Failure taxonomy

@table failures | RQ3 failure labels per policy

The dominant label for every policy is **retriever failure despite correct routing** (24 questions for four policies, 14 for AR-03): the policy searched the right source and the retriever did not return the answer. This is the upstream limit again. The control-specific failures are what distinguish the policies: AR-B0 *selects unnecessary sources* on 24 questions and starts with the wrong source on 12; AR-01 shows *structured intent failures* on 10; AR-02 ends with *insufficient evidence* on 18; AR-03's validator *falsely accepts* unsupported candidates on 18, it *never selects a required source* on 10 and *stops prematurely* on 8.

## Findings

1. **All five policies produced the same answers (F1 {{RQ3.AR-B1.answer_f1}}),** because the answers depend on what the retrievers can return, which is the same for every policy.
2. **The rule router chose sources significantly better than searching everything** and used fewer tokens and less time.
3. **The learned and agentic policies cost significantly more without better answers** (AR-01 {{RQ3.test.total_tokens.AR-01~AR-B1.delta}}, AR-03 {{RQ3.test.total_tokens.AR-03~AR-B1.delta}} tokens against the router).
4. **The agent wasted almost no retrieval ({{RQ3.AR-03.unnecessary_retrieval}}) but needed {{RQ3.AR-03.llm_calls}} model calls per question,** missed needed sources more often and was often accepted by its validator without support.
5. **The most frequent failure is not a control failure:** the policy searched the right source and the retriever did not return the answer.

## Inside one question

Side by side on a structured-only question, both the router and the agent return exactly the correct paper. The router does it with one rule decision, one search and one model call (468 tokens, 6.3 s); the agent needs three model calls (agent, draft answer and validator), 1,724 tokens and 24.2 s for the same answer.
