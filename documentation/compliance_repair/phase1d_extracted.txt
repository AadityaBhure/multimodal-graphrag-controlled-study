5: 1. Purpose and Freeze Boundary
6: This specification converts the nine retained literature methods into concrete, reproducible project implementations. It explicitly separates (a) what the source paper actually contributes from (b) the adaptation that will be implemented in this project. The purpose is controlled experimentation, not full end-to-end reproduction of every paper.
7: Scientific control rule
8: For RQ1, only context-selection/organization may change. For RQ2, the retrieved evidence pool must be cached and identical across fusion variants. For RQ3, the retriever implementations, context policy, fusion policy, final generator, and answer prompt must remain fixed; only the retrieval-control policy may change.

11: Status
12: Meaning
13: Frozen now
14: Method algorithms, method boundaries, class interfaces, method-specific hyperparameters/defaults, tuning policy, logging fields, fallbacks, and acceptance tests.
15: Deferred to Phase 2

17: Not allowed later

24: 3.2 Shared runtime rules
25: Generation temperature is fixed globally (target: 0 / deterministic decoding where supported).
26: A single final-answer prompt template is used across all variants in the same research question.
27: A single final generator model is used across all variants in the same experiment.
28: A single embedding model is used globally for query/node/chunk similarity unless a method requires a different representation; any exception must be named as an ablation.
29: Random seed is fixed (default seed = 42) for local algorithms and sampling.
30: Every context-producing method must satisfy MAX_CONTEXT_TOKENS. If the native method exceeds the budget, evidence is removed using that method's own ranking/order; no extra hidden reranker is allowed.
31: External internet retrieval is disabled in the main controlled experiments. CRAG's web-search branch is adapted to retrieval from an unqueried project source; a separate web-enabled ablation may be added later.
32: If evidence is insufficient, the final generator must be allowed to return INSUFFICIENT_EVIDENCE rather than invent an answer.
33: All intermediate LLM/tool calls count toward latency and cost metrics.

37: 4. RQ1 - Context Management Implementations
38: RQ1 compares how graph-backed evidence is bounded and organized before generation. All RQ1 methods receive the same query, the same indexed graph, the same chunk-to-graph provenance, the same embedding model, and the same final context-token budget.
39: RQ1 scope
40: Text-only and structured-only evidence is not modified by CM-01/02/03. Primary RQ1 analysis should focus on graph-dependent and multi-hop query strata. If text/SQL evidence is present in a mixed query, it is passed through a fixed baseline policy while only graph evidence changes.

42: 4.1 CM-01 - KG2RAG-Inspired Context Organization
43: Source mechanism: Semantic Top-k seed chunks -> m-hop KG expansion -> weighted connected components -> maximum spanning tree (MST) filtering -> DFS paragraph construction -> cross-encoder ranking -> retain evidence until chunk/token budget.
44: Paper-faithful basis: KG2RAG uses semantic seed retrieval, graph-guided expansion, and KG-based organization. The paper uses k=10 in the main setup, m=1 in the main expansion setup, constructs an MST per connected component, DFS-orders chunk text, and ranks MSTs using a cross-encoder over triplet representations.
45: Project implementation status: Adaptation: we reproduce the organization logic, not the paper's entire end-to-end RAG stack.
46: Input
47: run_kg2rag_context(    query: str,    chunks: ChunkStore,    graph: KnowledgeGraph,    chunk_graph_links: Mapping[chunk_id, list[triple]],    max_context_tokens: int,    config: KG2RAGConfig) -> ContextPackage
48: Frozen algorithm
49: 1. Embed query q using GLOBAL_EMBEDDER.2. Compute cosine similarity s(q, chunk) for all retrievable chunks.3. Select seed chunks Dq = TopK(k_seed=10).4. Get all graph triples whose source chunk is in Dq.5. Expand the graph m_hops=1 from those seed-linked entities.6. For every expanded triple (h,r,t,c):      edge_weight = s(q, source_chunk=c)      create undirected weighted edge h <-> t      preserve relation r and source chunk c as metadata.7. Split expanded graph into connected components B1..Bp.8. For each component Bi:      Ti = maximum_spanning_tree(Bi)      choose the highest-weight edge as the traversal root      DFS over Ti      append each source chunk once, in first-encounter order      build:        a) text_representation(Ti)        b) triplet_representation(Ti)9. Score every Ti with GLOBAL_RERANKER(query, triplet_representation(Ti)).10. Sort trees by reranker score descending.11. Add tree text representations in that order, deduplicating chunk IDs,    until max_context_tokens is reached.12. Return ContextPackage + diagnostics.

89: 4.2 CM-02 - G-Retriever-Inspired PCST Selection
90: Source mechanism: Query-node/edge similarity -> rank-based prizes -> Prize-Collecting Steiner Tree objective -> compact connected subgraph.
91: Paper-faithful basis: G-Retriever assigns descending prizes k..1 to the most query-relevant nodes/edges, zero to the rest, and maximizes node prizes + edge prizes - edge cost. The paper makes edge cost Ce adjustable; reported settings include Ce=1 for SceneGraphs and Ce=0.5 for WebQSP.
92: Project implementation status: Adaptation: only the PCST retrieval/subgraph selection is implemented. The paper's GNN, projection layer, graph soft prompt, and LLM fine-tuning are deliberately excluded from RQ1.
93: Input
94: run_pcst_context(    query: str,    graph: KnowledgeGraph,    max_context_tokens: int,    config: PCSTConfig) -> ContextPackage
95: Frozen algorithm
96: 1. Embed query q, every graph node text, and every edge text with GLOBAL_EMBEDDER.2. Compute cosine similarities:      sim_node(v) = cos(q, node_text(v))      sim_edge(e) = cos(q, edge_text(e))3. Select:      top k_node nodes      top k_edge edges4. Assign rank prizes:      highest ranked item -> k      ...      kth item -> 1      all unselected items -> 05. Define PCST objective:      maximize Σ node_prize + Σ edge_prize - |E_selected| * C_e      subject to selected subgraph being connected.6. Convert positive edge prizes to the virtual-node construction used by G-Retriever   when required by the PCST solver.7. Solve PCST with pcst_fast (or another fixed solver producing equivalent objective).8. Convert selected subgraph to deterministic text:      sort connected evidence by BFS from highest-prize node,      tie-break by node_id / edge_id.9. If textualization exceeds MAX_CONTEXT_TOKENS:      remove the lowest net-contribution leaf branch iteratively      (prize contribution - C_e), recomputing tokens after each removal.10. Return final connected subgraph + provenance + diagnostics.

132: 4.3 CM-03 - QAFD-RAG Query-Aware Flow Diffusion
133: Source mechanism: Query keyword extraction -> semantic seed nodes -> query-aware edge reweighting -> push/relabel-style flow diffusion -> support nodes define the retrieved subgraph.
134: Paper-faithful basis: QAFD-RAG is training-free. It computes node seeds from query semantics, dynamically reweights edges, injects mass into seeds, and discovers relevant graph support locally. The source reports task-dependent settings; its narrative QA experiments use alpha=10, a 40-node source budget and minimum flow 0.01, while sensitivity sections also study seed counts including 20 and alpha values including 10.
135: Project implementation status: Adaptation: preserve QAFD mechanics but freeze a resource-conscious source budget suitable for the project's local environment.
136: Input
137: run_qafd_context(    query: str,    graph: KnowledgeGraph,    max_context_tokens: int,    config: QAFDConfig) -> ContextPackage
138: Frozen algorithm
139: 1. Extract query keywords/concepts Kq using KEYWORD_EXTRACTOR.   Primary implementation: deterministic LLM JSON prompt; cache result by query_id.2. Embed every keyword and graph node with GLOBAL_EMBEDDER.3. score(v,q) = max cosine(keyword_i, node_v).4. Select N_seed=20 top nodes as seeds.5. For every edge reached during diffusion, compute the project's hybrid query-aware   edge weight implementation from the QAFD paper formulation.6. Set sink capacity T_v = 1 for all explored nodes.7. Inject source mass using alpha=10.8. Run push/relabel-style diffusion:      while excess_mass > convergence_epsilon and iter < N_max:          choose an active node deterministically from priority queue          compute query-aware outgoing weights          absorb capacity and distribute excess9. Keep nodes with x_v > support_threshold=0.01.10. Build the induced subgraph over retained nodes plus traversed retained edges.11. Rank retained nodes by x_v descending.12. Serialize evidence by descending x_v while preserving connecting edges.13. Enforce MAX_CONTEXT_TOKENS by dropping lowest-x leaf/peripheral evidence first.14. Return ContextPackage + flow diagnostics.

179: 5. RQ2 - Cross-Modal / Heterogeneous Fusion Implementations
180: RQ2 must isolate fusion. Therefore retrieval is run once per query with the fixed baseline retrievers, the resulting RetrievalBundle is cached, and all CF variants receive the exact same evidence IDs and raw evidence content. No fusion method is allowed to retrieve additional evidence.
181: Fusion invariant
182: CF-01, CF-02 and CF-03 may reorganize, select, summarize, or synthesize the cached evidence, but they may not issue new Text, Graph, or SQL retrieval calls.

222: 5.2 CF-02 - SAG-Inspired Dual-Path Contextual Fusion
223: Source mechanism: SAG combines a structural event/entity path with a direct semantic path. Its default final output is Kout=10, with an LLM selecting up to Kevent=5 structural events and the semantic path filling the remaining slots.
224: Project implementation status: Adaptation: the cached Graph + Structured evidence constitutes the structural path; cached Text evidence constitutes the semantic path. We do not rebuild SAG's event/entity retrieval index inside the RQ2 fusion experiment.

300: 6. RQ3 - Agentic Retrieval Implementations
301: RQ3 compares control policies. The underlying Text, Graph, and Structured/SQL tools are identical for all AR variants. The context policy is fixed to a deterministic budgeted baseline and the fusion policy is fixed to source-separated concatenation for primary RQ3 experiments.

346: 6.3 AR-02 - CRAG-Inspired Corrective Retrieval
347: Source mechanism: CRAG scores retrieved documents and triggers Correct, Incorrect, or Ambiguous actions. Original CRAG fine-tunes T5-Large, uses dataset-specific thresholds, refines document strips, and can invoke web search.
348: Project implementation status: Adaptation: keep the three-way correction policy, replace web search with project-source correction, and keep context refinement fixed so this remains an RQ3 control-policy experiment.
349: Evaluator specification
350: Primary evidence evaluator:- cross-encoder/ms-marco-MiniLM-L-6-v2 (local)- score each (query, evidence_item)- convert raw score to calibrated probability using validation-set Platt scaling- aggregate:    if max(score) >= UPPER -> GOOD    elif max(score) <= LOWER and all(score <= LOWER) -> BAD    else -> AMBIGUOUSThreshold calibration:- choose LOWER and UPPER on validation split only- grid:    LOWER in {0.20,0.25,0.30,0.35,0.40}    UPPER in {0.60,0.65,0.70,0.75,0.80}- objective: macro-F1 on GOOD/AMBIGUOUS/BAD retrieval-quality labels- require LOWER < UPPER- freeze chosen values before test evaluation.
351: Inference algorithm
352: 1. Use the shared rule router to choose the initial source.2. Retrieve from that source once.3. Evaluate evidence quality -> GOOD / AMBIGUOUS / BAD.4. GOOD:      stop retrieval and pass evidence to fixed downstream pipeline.5. AMBIGUOUS:      query the single highest-priority unqueried source from the shared rule router;      merge evidence; re-evaluate once.6. BAD:      query all remaining unqueried project sources in parallel;      merge evidence; re-evaluate once.7. Maximum correction rounds = 2 total evaluations after the first retrieval.8. If still BAD after all sources are exhausted:      return status='insufficient_evidence'.9. Final answer uses fixed context/fusion/generator.

385: 6.4 AR-03 - AGENT-G-Inspired Multi-Source Agent + Critic
386: Source mechanism: AGENT-G uses an agent, retriever bank, generator, validator, and commentor. Its action includes domain, topic entities, useful relations, and retriever selection. Rejected answers receive corrective feedback and the agent retries.
387: Project implementation status: Adaptation: extend the retriever bank from Text + Graph to Text + Graph + Structured/SQL while preserving the select-retrieve-generate-validate-comment loop.
388: Agent action schema
389: AgentAction = {  "iteration": int,  "source": "text" | "graph" | "structured" | "stop",  "retrieval_query": str,  "domain": str | null,  "entities": list[str],  "relations": list[str],  "structured_intent": str | null,  "reason_code": "textual" | "relational" | "numeric" | "hybrid" | "correction",  "stop_reason": str | null}
390: Frozen algorithm
391: Inputs:  query q  retriever bank {Text, Graph, Structured}  max iterations T=4  evidence_memory = []for t in 1..4:  1. Agent(q, previous_feedback, evidence_memory) -> AgentAction.  2. If action.source == stop:        break and generate from evidence_memory.  3. Execute exactly one retrieval tool for the selected source.  4. Add new non-duplicate evidence to evidence_memory.  5. Generator produces candidate_answer using:        q + fixed source-separated evidence_memory.  6. Validator receives:        q + candidate_answer + evidence_memory     and returns strict JSON:        {          "accept": true|false,          "error_type": "none|wrong_source|wrong_entity|wrong_relation|                        insufficient_evidence|unsupported_answer|structured_query_error",          "unsupported_claims": [...]        }  7. If accept=true:        return candidate_answer.  8. Commentor receives:        q + AgentAction + validator result     and returns concise corrective feedback for next iteration.  9. Prevent loops:        if the same normalized action is repeated twice with no new evidence:             feedback = "Previous action produced no new evidence. Choose a different source/action."             if repeated again -> stop with insufficient_evidence.After iteration 4:  - if last candidate is validator-accepted, return it  - else return INSUFFICIENT_EVIDENCE / best supported partial answer,    depending on evaluation protocol.
